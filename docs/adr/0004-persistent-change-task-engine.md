# 受管主机变更采用持久化异步任务引擎

所有经 root 管理代理执行的受管主机变更统一进入“变更任务”module，由 root 端权威动作目录固定常规、确认或回滚等级，并负责实时预览、事实摘要、全局串行、幂等、审计和恢复。网页与 CLI 共用该 module；现有管理脚本继续作为事实配置的执行 adapter，不复制或取代事实配置。

## 决策

- 任务引擎位于现有 root 管理代理的 implementation 内，使用单 worker 和有上限的 FIFO 队列，不新增第二个守护进程或内部 Socket seam。
- root-only SQLite 保存当前状态和追加式状态迁移；敏感载荷使用机器密钥短期加密，完成、取消或过期后删除，且不进入配置备份。
- 影响预览由 root 端根据实时事实配置生成，并与操作者、有效期和事实摘要绑定；执行前事实变化会使任务失效。
- 重复请求只返回原任务状态，不重复执行。执行中断后不自动重试，而是核验事实并等待用户发起新任务。
- 回滚变更必须由独立的已认证会话或 CLI 连接确认；其他同等权限管理员只能接管取消、回滚和恢复确认。
- 动作目录中的变更动作均标记为仅任务执行；即使调用方传入旧的 `confirmed=true`，管理 Socket 也会拒绝直接执行。网页与 CLI 只能调用任务预览、确认、取消和查询接口。
- 初始化、管理平面更新和卸载暂不由任务引擎执行，因为任务引擎不能可靠地替换或删除自身；这些生命周期操作必须在没有活动任务时运行。

## 考虑过的方案

- **保留同步请求**：会长期占用 HTTP 与 Unix Socket 请求，页面关闭或网络波动后无法可靠判断结果，也会继续复制确认流程。
- **建立独立 worker 进程**：当前只有一个执行 adapter，额外进程和 IPC seam 没有真实变化需求，先增加复杂度而没有增加 depth。
- **让网页指定变更等级或生成预览**：会把安全策略和事实理解泄漏到低权限网页，允许不同调用方产生漂移或降级风险。
- **完整事件溯源**：当前只需要可靠查询当前状态和追踪迁移；当前状态行加追加式迁移记录已足够，事件溯源的恢复与投影成本没有相应 leverage。

## 后果

变更将分阶段迁移，先建立任务引擎，再接管常规与确认变更，最后只在一次性测试机验证后接管回滚变更。状态迁移、并发确认、事实失效、崩溃恢复、敏感载荷、队列、adapter 契约和断网自动回滚测试是接管现有动作的硬门槛。
